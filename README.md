# FLU fleet — конвейер прошивки и обслуживания роботов

Робот, площадка и оператор описываются в YAML. Все конфиги — MikroTik, параметры
ArduPilot, сервер WireGuard, MediaMTX, арбитр, конфиги операторов — собираются из
этих описаний командой `fleet`. Руками на железе ничего не вводится.

## Быстрый старт

```bash
py -3.11 -m venv .venv
.venv\Scripts\pip install -e .[dev]
.venv\Scripts\fleet check
```

## Интерфейс для стенда

```bash
.venv\Scripts\fleet ui
```

Откроется `http://127.0.0.1:8765`. Там видны площадки и роботы, статус последнего
теста и пошаговая прошивка выбранного робота: регистрация → MikroTik → камеры →
ФК (список COM-портов подставляется сам) → сервер → приёмка. Там же переезд робота,
просмотр собранных конфигов и консоль с выводом команд.

Кнопки запускают те же команды `fleet`, что и в терминале, по одной за раз.
Интерфейс слушает только 127.0.0.1 и не отдаёт файлы из `secrets/`.
Пароль камер показывается по кнопке: он нужен для активации.

## Что где лежит

| Путь | Что это | Кто правит |
|---|---|---|
| `inventory/sites.yaml` | площадки и сервисный туннель | человек |
| `inventory/robots.yaml` | роботы (`site`, `slot` дописывает fleet) | человек + fleet |
| `inventory/operators.yaml` | операторы managed-площадок | человек |
| `base/platforms.yaml` | ревизии железа: порты MikroTik, ФК, камеры, failsafe | человек |
| `base/ardupilot-base.parm` | эталонные параметры с настроенного робота | человек |
| `base/ardupilot-ignore.txt` | калибровки, которые не заливаются и не сравниваются | человек |
| `templates/` | шаблоны MikroTik, ArduPilot, сервера, пакета заказчику | человек |
| `server/arbiter/` | арбитр управления и веб-панель | человек |
| `fleet/` | сам инструмент | человек |
| `secrets/` | ключи WireGuard и пароли (**не в git**) | fleet |
| `build/` | собранные конфиги и отчёты (**не в git**) | fleet |

## Адресный план

Внутри каждого робота сеть одинаковая:

| Адрес | Устройство | Порт MikroTik (flu-v1) |
|---|---|---|
| 192.168.88.1 | MikroTik | — |
| 192.168.88.2 | ФК / сетевой адаптер ФК, MAVLink TCP 5760 | ether2 |
| 192.168.88.11 | камера 1 | ether3 |
| 192.168.88.12 | камера 2 | ether4 |
| 192.168.88.100–199 | DHCP: стендовый ноутбук | ether5 |

Снаружи робот виден через туннель своей площадки. Адреса выводятся из `slot`
(номер робота на площадке, он же MAVLink SYSID):

- **туннель** — `tunnel + 1 + slot`; сервер площадки — `.1`;
- **устройства** — блок `/28` из `robot_lans`: MikroTik делает netmap этого блока в `192.168.88.0/28`.
  Например, на `flu-acme` у робота со slot 2 камера 2 видна как `10.150.16.28`;
- **операторы** — `operators + id оператора`.

Сети задаются на площадке, поэтому подсеть, выделенную заказчиком, можно взять как есть.
`fleet check` не пропустит пересечений между площадками, с `192.168.88.0/24` и с CGNAT `100.64.0.0/10`.

## Три сценария

| | Сценарий | `kind` | Что делает fleet |
|---|---|---|---|
| 1 | Наш сервер | `managed` | `deploy-server --site` ставит отдельный экземпляр стека под заказчика. Несколько экземпляров живут на одном VPS: каждый на своём порту WireGuard и своём адресе в туннеле |
| 2 | Сервер заказчика, обслуживаем мы | `managed` | то же самое, только `host` — VPS заказчика (Ubuntu/Debian, 1 vCPU, 1–2 ГБ, публичный IP, SSH-доступ для нас) |
| 3 | Свой сервер заказчика | `external` | `fleet kit --site` собирает пакет для их администратора: пиры WireGuard, адреса, отдельно пароли камер |

Стек managed-площадки: WireGuard (`wg-quick`), MediaMTX и арбитр в Docker. Сервер
не пересылает трафик между пирами: операторы работают только с сервисами сервера.

`endpoint` площадки — всегда DNS-имя. Тогда площадку можно перенести на другой сервер
(сценарий 1 → 2), не трогая роботов: деплой на новый host с теми же ключами
из `secrets/`, затем смена DNS.

## Новый робот

1. Добавьте робота в `inventory/robots.yaml` (`id`, `serial`, `platform`, `site`).
2. Выполните `fleet provision --id 4`. Команда выдаст slot и ключи, соберёт конфиги в `build/robots/flu-004/` и напечатает чек-лист для стенда.
3. **MikroTik.** Netinstall с Configure script `robot.rsc` (`netinstall-cli -r -s robot.rsc ...`). Если на роутере уже стоит RouterOS: `fleet bench mikrotik --id 4 --password <с наклейки>`. Команда проверит отпечаток конфига и снимет эталон для поиска дрейфа.
4. **Камеры.** Активируйте их паролем из вывода `provision`, включите в ether3 и ether4 и выполните `fleet bench cameras --id 4`.
5. **ФК** (по USB): `fleet fc --id 4 --connect COM5 --push --reboot`.
6. **Сервер.** Для managed-площадки: `fleet deploy-server --site <площадка>`. Для external: `fleet kit --site <площадка>`.
7. **Приёмка:** `fleet test --id 4`. Отчёт сохраняется в `build/reports/`.

## Переезд на другую площадку

```bash
fleet move --id 4 --to globex
```

1. На новой площадке появляется пир робота: для managed — автоматический деплой, для external — подтверждение, что заказчик добавил пира.
2. На MikroTik рядом со старым туннелем поднимается новый, с автооткатом через 10 минут.
3. Есть handshake — переезд подтверждается, старый туннель удаляется. Нет — изменения сразу откатываются, и робот остаётся на месте.

Удалённый доступ к MikroTik идёт по сервисному туннелю, а без него — через SSH-сервер managed-площадки.
`slot` по возможности сохраняется, чтобы не менять SYSID в ФК.

## Операторы и передача робота

Оператор импортирует свой конфиг из `build/sites/<площадка>/operators/` в WireGuard.
Там же лежит `README.md` с адресами роботов и камер. Дальше оператор:

- открывает панель `http://<сервер площадки>:8080`: там видно, кто чем владеет, и там же робота можно взять, передать, освободить или остановить;
- подключает QGroundControl или Mission Planner по TCP к `<сервер>:5760+slot` (GCS sysid остаётся 255);
- смотрит видео по `rtsp://<сервер>:8554/<робот>-cam1` или по WebRTC на порту 8889.

Правила арбитра:
- телеметрия идёт всем;
- команды проходят только от владельца;
- не-владелец может читать параметры и миссию и нажать «Стоп»;
- heartbeat к роботу проходит только от владельца, поэтому если владелец пропал, через `FS_GCS_TIMEOUT` секунд робот встаёт в Hold;
- при передаче арбитр сам ставит робота в Hold. Новый владелец принимает робота, только когда уже подключён к нему;
- диспетчер может забрать робота принудительно;
- всё пишется в журнал `state/audit.jsonl` на сервере.

## Секреты

`secrets/` в git не попадает. **Без него площадки нельзя обслуживать**: ключи
серверов и роботов не восстановить. fleet не пересоздаёт потерянный ключ сервера
молча, если на площадке уже есть роботы (`--new-key` — только осознанно).
Для командной работы зашифруйте каталог через sops + age и храните его в git
или держите резервную копию в надёжном месте.

## Тесты

```bash
.venv\Scripts\pytest
```

Покрыто:
- проверка inventory и адресный план;
- сборка всех конфигов и согласованность ключей между роботом и сервером;
- скрипты переезда;
- разбор параметров;
- правила арбитра и живой прогон арбитра с фейковым роботом и тремя операторами: захват, передача с Hold, перехват, фильтр heartbeat, перечитывание конфига.

## Проверить на железе

Каркас собран и протестирован без железа. Перед боевым использованием проверьте
на одном роботе и одном сервере:

**MikroTik:**
- [ ] `robot.rsc` применяется целиком через netinstall `-r -s` и через `reset-configuration run-after-reset`. Если какая-то строка не прошла, отпечаток в `fleet bench mikrotik` не совпадёт; причину смотрите в `/log print`;
- [ ] имена портов (`ether1..5`) и WAN (`ethernet` или `lte`) соответствуют вашей модели (`base/platforms.yaml`);
- [ ] `reset-configuration` по SSH проходит без интерактивного подтверждения;
- [ ] автооткат при переезде: `:execute` с `:delay` переживает закрытие SSH-сессии;
- [ ] RouterOS заново резолвит DNS-имя endpoint WireGuard после смены IP сервера. Если нет — нужен скрипт в планировщике.

**Полётный контроллер:**
- [ ] сетевой адаптер ФК работает TCP-сервером на `192.168.88.2:5760`. Это настраивается утилитой производителя адаптера; другой вариант — `fc.link: ardupilot-net`;
- [ ] имена параметров вашей прошивки: `legacy` (SYSID_*) или `mav` (MAV_*), см. `fc.param_names`;
- [ ] MAVLink по TCP через LTE: задержка команд при потерях пакетов. Если мешает, следующий шаг — UDP-транспорт в арбитре.

**Камеры:**
- [ ] смена IP через ISAPI (Hikvision) или CGI (Dahua) на ваших моделях; у Dahua интерфейс может называться `eth2`.

**Сервер:**
- [ ] `docker compose up --build` арбитра и MediaMTX `1.21.1` на сервере;
- [ ] WebRTC через туннель.

Не автоматизировано:
- активация камер и смена их пароля;
- прошивка самого ArduPilot (`.apj`): делается uploader.py или Mission Planner;
- калибровки компаса и IMU.
