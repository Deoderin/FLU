# UGV Quick Setup — прошивка та обслуговування НРК

НРК (наземні роботизовані комплекси), майданчики й оператори описуються в YAML.
Усі конфіги — MikroTik, параметри ArduPilot, сервер WireGuard, MediaMTX, арбітр,
конфіги пілотів і операторів — збираються з цих описів. Руками на залізі нічого не вводиться.

Для людей програма зветься **UGV Quick Setup**, у терміналі це команда `fleet`.

**Покрокова інструкція «чистий ноутбук + порожній сервер → готовий НРК» зі скріншотами:
[docs/flow.md](docs/flow.md).**

## Швидкий старт

На ноутбуці: двічі клацнути **`setup.cmd`**. Установник поставить Python 3.14, WireGuard
і fleet, створить на робочому столі ярлик «UGV Quick Setup» (старий «FLU fleet», якщо є, прибирає)
і відкриє майстер.

Далі програма запускається ярликом «UGV Quick Setup» або `fleet-ui.cmd` у теці репозиторію.
Майстер відкривається у власному вікні (WebView2 — рушій Edge, вбудований у Windows 10/11), без браузера;
закрили вікно — програма завершилась. `fleet-ui.cmd` при цьому:

- ще не встановлено — запускає `setup.cmd`;
- після `git pull` змінився `pyproject.toml` — сам оновлює залежності;
- програма вже працює — відкриває ще одне вікно до того самого майстра.

Браузерний варіант лишився: `fleet ui` (`http://127.0.0.1:8765`).

### Окрема програма без Python

`build-exe.cmd` збирає `dist\UGV Quick Setup\` (і zip поруч): `UGV Quick Setup.exe` — вікно майстра,
`fleet.exe` — ті самі команди з консолі, поруч — `base\`, `templates\`, `server\`, `inventory.example\`.
На ноутбуці, куди передаєте, потрібен лише WireGuard; Python не потрібен. Теку кладіть туди, де шлях
латиницею й можна писати (не в Program Files): `inventory\`, `secrets\` і `build\` програма створює поруч
із собою. Ярлик на робочому столі з'являється сам під час першого запуску.
Свої `inventory\` і `secrets\` у збірку не потрапляють — лише шаблони.
Зібрані версії лежать у Releases репозиторію, як їх випускати — [docs/release.md](docs/release.md),
що змінилось — [CHANGELOG.md](CHANGELOG.md).

Для розробки (тести, скріншоти документації):

```powershell
py -3.14 -m venv .venv
.venv\Scripts\pip install -e .[dev,docs]
.venv\Scripts\pytest
```

Підтримується Python 3.11–3.14. На 3.15 поки немає готових збірок `pymavlink` і `PyYAML`.

Мова: українська за замовчуванням, англійська — `fleet --lang en ...` або `FLEET_LANG=en`.
У веб-інтерфейсі й панелі операторів мова перемикається кнопками UK / EN у шапці.

## Майстер (сервер hub)

Ярлик «UGV Quick Setup» (`fleet app`) відкриває вікно майстра, `fleet ui` — те саме в браузері на
`http://127.0.0.1:8765`. Головна сторінка — покроковий майстер:

| # | Крок | Що відбувається |
|---|---|---|
| 1 | Пілот і НРК | пілот зі списку (ті, чиї ключі на цьому ноутбуці) або «+ Новий пілот»; заводський номер НРК латиницею. Щоб додати пілоту ще один НРК, виберіть його й введіть новий номер |
| 2 | Сервер | «Відкрити термінал сервера» (адреса, користувач), «Скопіювати команду», вставити на сервері. Команда сама ставить WireGuard або лише додає пілота й НРК |
| 3 | Відповідь сервера | вставити рядок `FLU1:...:END`: адреса й ключ сервера, номер пілота, слот НРК записуються в `inventory/` |
| 4 | Пілот у WireGuard | тунель цього пілота на ноутбуці; «Файл тунелю для ноутбука пілота» — конфіг, який пілот імпортує у свій WireGuard |
| 5 | Роутер | «Перевірити підключення» й «Прошити роутер» — кабелем у порт 5 або без кабелю через спільну мережу; зібраний НРК — «Перепрошити через тунель». Перед прошивкою програма сама знаходить камери й ФК у портах 2–4 на їхніх адресах і показує, кого знайшла; без когось не прошиває, доки не вирішите (див. «Адресний план» і «Роутер») |
| 6 | Готово | адреса для QGroundControl (TCP, MAVLink), посилання камер (основний і легкий потік, з логіном і паролем), «Прописати камери в Termite», «Перевірити зв'язок з НРК» — приймальний тест |
| 7 | Передати НРК або видалити із сервера | службові команди для сервера (див. «Спільний сервер hub»). У зібраній програмі передачі поки немає — картка зветься «Видалити із сервера» |

**AWS.** На серверах Amazon вхід лише за файлом ключа `.pem`: у кроці 2 є кнопка «Вибрати файл ключа»,
користувач `ubuntu`. Інший шлях — EC2 → сервер → Connect → EC2 Instance Connect.
Порт WireGuard відкривається в Security Group: **Inbound** rules → Custom **UDP**, `51820` (або той, що назве
сервер), джерело `0.0.0.0/0`. Це безпечно: на пакети без потрібного ключа WireGuard не відповідає.
SSH (`22`) для всіх не відкривайте — досить My IP або EC2 Instance Connect.
Під сервер одразу візьміть **Elastic IP**: звичайна адреса AWS міняється після зупинки й запуску сервера,
а вона зашита в кожен прошитий роутер.

`/advanced` — розширений режим для інженера: майданчики, таблиця НРК, покрокова прошивка
(реєстрація → MikroTik → камери → польотний контролер → сервер → приймальний тест),
переїзд, зібрані конфіги й консоль. Пароль камер там показується за кнопкою: він потрібен для активації.

Кнопки запускають ті самі команди `fleet`, що й у терміналі, по одній за раз.
Інтерфейс слухає лише 127.0.0.1 і не віддає файли з `secrets/`.

| `inventory/robots.yaml` | НРК (`site`, `slot` і `devices` — адреси пристроїв, знайдені під час прошивки, — дописує fleet) (**не в git**) | людина + fleet |
| `inventory/operators.yaml` | пілоти й оператори (**не в git**) | людина + fleet (hub) |

| `base/platforms.yaml` | ревізії заліза: порти MikroTik, ФК, камери (виробник, логін і пароль, RTSP-шляхи), failsafe | людина |
| `base/ardupilot-base.parm` | еталонні параметри з налаштованого НРК | людина |
| `base/ardupilot-ignore.txt` | калібрування, які не заливаються й не порівнюються | людина |
| `templates/` | шаблони MikroTik, ArduPilot, сервера, файлів підключення | людина |
| `server/hub/flu-hub.sh` | скрипт сервера hub: їде всередині команди з кроку 2 | людина |
| `server/arbiter/` | арбітр керування та панель операторів | людина |
| `fleet/` | сам інструмент; `fleet/app.py` — вікно майстра, `fleet/termite.py` — камери в Termite | людина |
| `packaging/`, `build-exe.cmd` | збірка окремої програми (PyInstaller) і її значок | людина |
| `dist/` | зібрана програма й zip для релізу (**не в git**) | `build-exe.cmd` |
| `CHANGELOG.md`, `docs/release.md` | що змінилось у версіях і як випустити нову | людина |
| `tests/` | тести; тестовий інвентар — у `tests/fixtures/` | людина |
| `secrets/` | ключі WireGuard пілотів, НРК і серверів, паролі роутерів і камер (**не в git**) | fleet |
| `build/` | зібрані конфіги (`robots/nrk-NNN/robot.rsc`, тунелі пілотів `sites/<майданчик>/operators/<пілот>.conf`), звіти, журнали (**не в git**) | fleet |

На сервері hub, у `/etc/wireguard/`:

| Файл | Що це |
|---|---|
| `flu-peers.tsv` | головний список: пілоти й НРК, їхні номери, ключі й пілот-власник НРК |
| `flu.conf` | конфіг інтерфейсу `flu`, кожна команда збирає його заново з `flu-peers.tsv` |
| `flu-acl.sh` | правила iptables: який пілот до якого НРК (ланцюжок `flu-acl`) і куди йде телеметрія, яку адаптер ФК шле сам (ланцюжки `flu-tel` у filter і nat) |
| `flu.key` | закритий ключ сервера |

Номери пілотів і слоти НРК роздає сервер, ноутбук лише записує їх із відповіді.

## Адресний план

Стандартна мережа всередині НРК:

| Адреса | Пристрій | Порт MikroTik (flu-v1) |
|---|---|---|
| — | Starlink (WAN) | ether1 |
| 192.168.88.1 | MikroTik | — |
| 192.168.88.108 | передня камера (`cam1`) | ether2 |
| 192.168.88.109 | задня камера (`cam2`) | ether3 |
| 192.168.88.2 | ФК / мережевий адаптер ФК, MAVLink TCP 5760 | ether4 |
| 192.168.88.200–249 | DHCP: ноутбук на стенді | ether5 |

**Пристрої не обов'язково переналаштовувати.** Роутер завжди `192.168.88.1`, а камери й ФК можуть лишатися
на своїх адресах. Перед прошивкою програма дивиться, хто стоїть у портах `cam1` / `cam2` / `fc` (за портом,
а не за адресою, тож передню й задню камери не переплутати) і на якій адресі, наприклад
`192.168.15.108` / `.109` / `.253`. Знайдене записується в `robots.yaml` (`devices`, разом із MAC), і роутер
прошивається під ці адреси: бере собі адресу в їхній мережі (`.1`, а якщо її зайняв пристрій — `.254`),
веде до них тунель і закріплює їхні адреси в DHCP. Дві камери на одній адресі (заводській
`192.168.1.108`) роутер розвести не може — програма про це каже, одній камері адресу треба змінити (Dahua ConfigTool).

Як шукаються пристрої: спершу 10 секунд слухаємо мережу (`/tool ip-scan` без адрес). Камера, яку ніхто не
дивиться, може мовчати хвилинами, тож тих, кого не почули, програма опитує сама: роутер тимчасово бере адресу
в імовірній мережі (де вже знайшлися інші пристрої, адреси з минулої прошивки, заводська мережа камер) і
опитує всі 254 адреси — на ARP пристрій відповідає, навіть коли мовчить. Мережі, що вже є на інших
інтерфейсах (Starlink у порту 1, тунелі), не чіпаються; тимчасові адреси прибираються одразу. Пристрої з лінком,
що ще вантажаться, програма чекає до півтори хвилини. Якщо камери чи ФК так і не знайшлося (і адреси з минулої
прошивки немає), роутер **не прошивається**: майстер показує в кроці 5, кого бракує, і пропонує «Шукати ще раз»
або «Прошити без них» (`--allow-missing`).

Технічне ім'я НРК — `nrk-<id>` (наприклад, `nrk-001`): воно ж ідентифікатор
MikroTik, імена файлів і відеопотоків. Ззовні НРК видно через тунель свого
майданчика; адреси виводяться зі `slot` (номер НРК на майданчику, він же MAVLink SYSID):

- **тунель** — `tunnel + 1 + slot`; сервер майданчика — `.1`;
- **пристрої** — блок `/28` з `robot_lans`: роутер і ФК — `.1` і `.2` блоку через netmap у `192.168.88.0/28`,
  камери — `.8` / `.9` блоку окремим dst-nat на `192.168.88.108` / `.109`. Якщо пристрій стоїть на іншій
  адресі, знайденій під час прошивки, роутер веде dst-nat туди.
  Наприклад, на майданчику з `robot_lans: 10.150.16.0/20` у НРК зі slot 3 передня камера видна як `10.150.16.40`;
  точні адреси НРК показує крок 6 майстра;
- **оператори й пілоти** — `operators + id`.

Камерам і адаптеру ФК шлюз не потрібен: на запити з тунелю роутер підставляє себе відправником
(masquerade), тож пристрої відповідають йому. Пілотам до камер і ФК свого НРК дозволено будь-який трафік:
MAVLink по TCP чи UDP, RTSP і RTP по UDP, ping. Великі UDP-пакети відео роутер дробить під тунель MTU 1280,
а не викидає. Інтернету в камер і ФК немає.

**Телеметрія, яку адаптер ФК шле сам.** Деякі адаптери (Waveshare у режимі UDP тощо) не чекають підключення,
а самі шлють MAVLink на заданий адрес — часто на старий наземний ноутбук (`10.66.66.2` тощо). Такий UDP роутер
відправляє на сервер майданчика, а сервер — пілоту, якому НРК належить зараз (ланцюжки `flu-tel` у
`flu-acl.sh`); відповіді пілота, тобто керування, йдуть назад тим самим шляхом. Адаптер переналаштовувати не
треба, а в Termite / QGroundControl досить стандартного AutoConnect UDP (порт 14550).

MTU усіх тунелів WireGuard — **1280**: на роутерах, на сервері й у тунелях пілотів.

`fleet check` не пропустить перетинів між майданчиками, з `192.168.88.0/24` і з CGNAT `100.64.0.0/10`.

## Сценарії

| | Сценарій | `kind` | Що робить fleet |
|---|---|---|---|
| 0 | Наш сервер однією командою | `hub` | майстер дає команду для сервера (`flu-hub.sh`): лише WireGuard, пілоти ходять до своїх НРК напряму через сервер |
| 1 | Наш сервер зі стеком | `managed` | `deploy-server --site` ставить окремий екземпляр стеку під замовника. Кілька екземплярів живуть на одному VPS: кожен на своєму порту WireGuard і своїй адресі в тунелі |
| 2 | Сервер замовника, обслуговуємо ми | `managed` | те саме, лише `host` — VPS замовника (Ubuntu/Debian, 1 vCPU, 1–2 ГБ, публічний IP, SSH-доступ для нас) |
| 3 | Власний сервер замовника | `external` | `fleet kit --site` збирає файли підключення для їхнього адміністратора: піри WireGuard, адреси, окремо паролі камер |

Стек managed-майданчика: WireGuard (`wg-quick`), MediaMTX і арбітр у Docker. Сервер
не пересилає трафік між пірами: оператори працюють лише із сервісами сервера.

`endpoint` майданчика краще задавати DNS-ім'ям. Тоді майданчик можна перенести
на інший сервер (сценарій 1 → 2), не чіпаючи НРК: розгортання на новий host з тими
самими ключами з `secrets/`, потім зміна DNS.

## Новий НРК

Детально, зі скріншотами — у [docs/flow.md](docs/flow.md). Коротко — майстер, кроки 1–6. Те саме з терміналу (hub):

```powershell
.venv\Scripts\fleet hub-command --pilot ivan --serial PF-01
.venv\Scripts\fleet hub-apply --text "FLU1:...:END"
.venv\Scripts\fleet wg-install --site main --pilot ivan
.venv\Scripts\fleet bench mikrotik --id 3 --password <з наліпки>
.venv\Scripts\fleet bench cameras --id 3
.venv\Scripts\fleet fc --id 3 --connect COM5 --push --reboot
.venv\Scripts\fleet test --id 3
```

`hub-command` друкує команду, яку вставляють на сервері; `hub-apply` приймає рядок відповіді сервера.
Для managed-майданчика замість перших двох — `fleet provision --id 3` і `fleet deploy-server --site <майданчик>`,
для сервера замовника — `fleet kit --site <майданчик>`. Звіт приймального тесту — у `build/reports/`.

**Тунелі пілотів у WireGuard.** У кожного пілота свій тунель `<майданчик>-<пілот>`, наприклад `main-pilot-2`,
тож на одному ноутбуці технік може налаштувати кількох пілотів. Усі вони ведуть у ті самі мережі НРК,
тому працює лише один: вмикаючи тунель пілота, програма вимикає тунелі інших пілотів цього ноутбука
(вони лишаються в застосунку WireGuard). Старі тунелі з тестовою назвою `flu-main*` прибираються зовсім.

**Камери** за замовчуванням Dahua (`base/platforms.yaml`): логін і пароль однакові на всіх НРК і йдуть
прямо в посилання для QGroundControl; основний потік — `/cam/realmonitor?channel=1&subtype=0`, легкий —
`subtype=1`. Переносити камери на `.108` / `.109` не обов'язково: роутер прошивається під їхні адреси
(див. «Адресний план»). Якщо все ж треба, `fleet bench cameras` переносить передню (порт 2) на `.108`, а задню
(порт 3) на `.109` із заводської адреси або старих `.8` / `.9`; поки переноситься одна, порт другої вимкнено.
Переносити можна лише кабелем.

## Роутер

**Кабелем:** ноутбук у порт 5, «Прошити роутер» (або `fleet bench mikrotik`). Роутер скидається
й перезавантажується вже з конфігом НРК. fleet перевіряє відбиток конфігу й знімає еталон для пошуку дрейфу.

**Без кабелю, через спільну мережу.** Уже прошитий НРК, що вийшов у мережу портом 1 (Starlink у режимі
роутера чи будь-яка інша мережа), можна перепрошити з ноутбука в тій самій мережі (Wi-Fi того самого Starlink).
Програма знаходить роутер за ім'ям НРК (`nrk-003`) і сама підставляє його пароль з `secrets/`.
З боку WAN роутер, крім ping, приймає лише ssh і пошук MikroTik (MNDP), і лише з приватних адрес;
камери, ФК і WinBox звідти закриті. Роутери, прошиті до появи цього правила, вперше перепрошиваються кабелем.

**Без кабелю, через тунель (hub).** Зібраний НРК у полі пілот-власник бачить через свій тунель, тож роутер
можна перепрошити з його ноутбука звідки завгодно: крок 5 → «Перепрошити через тунель» (тунель пілота з кроку 4
має бути ввімкнено) або `fleet bench mikrotik --id 3 --tunnel`. Програма заново шукає камери й ФК, роутер
перезавантажується й повертається через тунель; 1–2 хвилини НРК без зв'язку, тож не робіть цього на ходу.

Новий роутер — пароль з наліпки (рядок «Password», не Wi-Fi); уже прошитий — програма пробує й свій пароль,
а також порожній. Якщо роутер відповів, але пароль не підійшов, програма так і каже й підказує перевірити
пароль у браузері (`http://192.168.88.1`, користувач `admin`).

**Скидання.** Кнопку Reset відпускають, щойно індикатор почне блимати (≈5 с). Якщо тримати, доки він не
засвітиться рівно, вмикається режим CAP: усі порти в мості `bridgeLocal`, адреса від мережі в порту 1,
`192.168.88.1` немає. Програма такий роутер упізнає й прошиває за його поточною адресою, а після скидання
чекає його на обох адресах. Без адреси (у порту 1 нічого) підкаже скинути ще раз правильно.

**Порт ноутбука.** USB-Ethernet перехідник програма бачить так само, як вбудований порт. Якщо дротового
порту немає зовсім, вона шукає НРК через Wi-Fi і пояснює, що без кабелю видно лише вже прошитий НРК.

**Камери й ФК у тесті.** Роутер пінгує передню й задню камери та адаптер ФК на тих адресах, куди веде тунель;
хто не відповідає на ping, але є в ARP, теж рахується. Не відповідає — FAIL з номером порту: перевірте живлення
й кабель, а якщо пристрій на іншій адресі — перепрошийте роутер, прошивка знайде його сама.

**Дрейф.** Приймальний тест порівнює `/export` роутера з еталоном. Те, що RouterOS міняє сам, не рахується:
коментарі на кшталт `# Interface not active` (поки в порту 1 немає мережі) і часовий пояс, визначений автоматично.

## Termite QGroundControl

Termite — форк QGroundControl 4.3–4.4 від Tencore з кількома камерами. Кнопка «Прописати камери в Termite»
у кроці 6 записує в його налаштування (`%APPDATA%\tencore.org\Termit QGroundControl Daily.ini`) обидві
камери НРК: `front` і `back`, основний потік у RTSP URL, легкий — у Secondary RTSP URL, low latency.
Посилання — `rtspt://` (відео по TCP): по UDP через Starlink і тунель Termite лишається чорним, а сам на TCP,
як VLC чи звичайний QGroundControl, не перемикається.
Решту налаштувань Termite не чіпає. Termite має бути закритим: відкритий під час закриття перезапише файл.

- **Тека Termite — лише латиницею.** Termite на базі QGC 4.x передає GStreamer шлях до своїх модулів у
  неправильному кодуванні, і з кирилицею в шляху відео не працює зовсім (у журналі
  `gst_element_factory_make('tee') failed`). Скопіюйте теку програми, наприклад, у `C:\Termit` і запускайте
  звідти; ярлик на робочому столі може лежати де завгодно. Програма попереджає, якщо знайде Termite в теці з кирилицею.
- **Телеметрія**, яку адаптер ФК шле сам, приходить на AutoConnect UDP (порт 14550) — нічого додавати не треба.
- **Пульт** (джойстик) налаштовується в самому Termite; калібрування й кнопки зберігаються в його
  налаштуваннях на комп'ютері (розділ `[Joysticks]`), а не в пульті.

## Спільний сервер hub

**Хто бачить НРК.** НРК бачить лише той пілот, з яким його додали командою на сервері або якому його
передали: сервер пропускає пілота тільки до мереж його НРК (ланцюжок iptables `flu-acl`, файл
`/etc/wireguard/flu-acl.sh`). Інші пілоти цього сервера до НРК не дістануться, навіть якщо змінять свій конфіг WireGuard.

**Кілька ноутбуків на одному сервері.** Ім'я пілота й заводський номер НРК закріплені на сервері
за ключем. Той самий ноутбук може повторювати команду скільки завгодно. Інший ноутбук з уже зайнятим
ім'ям чи номером отримає відмову й нічого не зламає: виберіть інше ім'я (наприклад, `ivan-2`).

Нових пілотів і НРК сервер додає без розриву наявних тунелів і сам ставить маршрути до всіх пірів.

Службові команди працюють за іменами, ключі для них не потрібні, тож їх можна давати з будь-якого
ноутбука. У майстрі це картка 7 «Передати НРК або видалити із сервера», у терміналі — `fleet hub-admin`.
Команда так само вставляється на сервері; відповідь у програму вставляти не треба.

**Передача НРК поки вимкнена в зібраній програмі** (`UGV Quick Setup.exe`): її ще не перевірено в полі.
Там немає ні пункту в картці 7, ні `hub-admin --give`, а повторне додавання НРК з іншим пілотом сервер
відхилить (`--no-give`). У версії з репозиторію передача є — для перевірки. Після перевірки приберіть `give`
з `EXPERIMENTAL` у `fleet/__init__.py`; разово ввімкнути в зібраній — змінна середовища `FLEET_EXPERIMENTAL=1`.

| Що | Команда | Наслідок |
|---|---|---|
| Передати НРК | `fleet hub-admin --give PF-01 --to petro` | новий пілот одразу бачить НРК, попередній — ні; сервер друкує адреси НРК (MAVLink, камери) |
| Видалити пілота | `fleet hub-admin --remove-pilot petro` | ім'я звільняється; НРК пілота лишаються без пілота, їх треба передати |
| Видалити НРК | `fleet hub-admin --remove-robot PF-01` | слот звільняється; щоб повернути НРК, додайте його знову й перепрошийте роутер |

Пілот, якому передають НРК, має бути вже доданий на сервер зі свого ноутбука. НРК без пілота
(додані до появи правил доступу або після видалення пілота) не бачить ніхто: сервер перелічує їх
після кожної команди.

Перевірити сервер: `sudo wg show flu` (хто підключений), `sudo iptables -S flu-acl` (хто до якого НРК),
`sudo iptables -t nat -S flu-tel` (кому йде телеметрія, яку адаптери ФК шлють самі),
`sudo tcpdump -ni flu udp port 14550` (чи йде MAVLink по UDP).

## Переїзд на інший майданчик

```bash
fleet move --id 4 --to customer-vps
```

1. Новий майданчик отримує пір НРК: для managed — автоматичне розгортання, для external — підтвердження, що замовник додав пір.
2. На MikroTik поруч зі старим тунелем піднімається новий, з автовідкатом через 10 хвилин.
3. Є handshake — переїзд підтверджується, старий тунель видаляється. Немає — зміни одразу відкочуються, НРК лишається на місці.

Віддалений доступ до MikroTik іде сервісним тунелем, а без нього — через SSH-сервер managed-майданчика.
`slot` за можливості зберігається, щоб не міняти SYSID у ФК.

## Оператори й передача НРК (managed)

Оператор імпортує свій конфіг з `build/sites/<майданчик>/operators/` у WireGuard.
Там само лежить `README.md` з адресами НРК і камер. Далі оператор:

- відкриває панель `http://<сервер майданчика>:8080`: там видно, хто чим володіє, і там же НРК можна взяти, передати, звільнити або зупинити;
- підключає QGroundControl або Mission Planner по TCP до `<сервер>:5760+slot` (GCS sysid лишається 255);
- дивиться відео за `rtsp://<сервер>:8554/<нрк>-cam1` або через WebRTC на порту 8889.

Правила арбітра:
- телеметрія йде всім;
- команди проходять лише від власника;
- не-власник може читати параметри й місію та натиснути «Стоп»;
- heartbeat до НРК проходить лише від власника, тож якщо власник зник, через `FS_GCS_TIMEOUT` секунд НРК стає в Hold;
- під час передачі арбітр сам ставить НРК у Hold. Новий власник приймає НРК, лише коли вже підключений до нього;
- диспетчер може забрати НРК примусово;
- усе пишеться в журнал `state/audit.jsonl` на сервері.

## Секрети

`secrets/` у git не потрапляє. **Без нього майданчики не можна обслуговувати**: ключі
серверів, пілотів і НРК, паролі роутерів не відновити. Пароль прошитого роутера є лише там.
fleet не перестворює втрачений ключ сервера мовчки, якщо на майданчику вже є НРК
(`--new-key` — лише свідомо). Робіть резервну копію `secrets/`; для командної роботи
зашифруйте теку через sops + age і зберігайте в git.

Ваш `inventory/` (сервер, пілоти, НРК) теж у git не потрапляє: у репозиторії лише шаблони
`inventory.example/`, тож разом із кодом ваші дані до інших не підуть. Зберігайте `inventory/`
у резервній копії разом із `secrets/`.

Інший ноутбук без `secrets/` не може працювати з пілотами й НРК цього ноутбука — лише заводити нових
(з іншими іменами) або давати службові команди за іменами.

## Тести

```bash
.venv\Scripts\pytest
```

Тести працюють на тестовому інвентарі з `tests/fixtures/` і на шаблонах `inventory.example/`
та не чіпають ваш `inventory/`. Покрито:
- перевірка інвентарю й адресний план (netmap, dst-nat камер і ФК);
- пошук пристроїв у портах роутера (на справжньому виводі `ip-scan`), опит мовчазних, зупинка прошивки без них,
  перевірка камер і ФК у приймальному тесті, конфіг роутера під їхні адреси;
- збирання всіх конфігів і узгодженість ключів між НРК і сервером;
- скрипт сервера hub із заглушкою `wg`: пілоти й НРК, доступ `flu-acl`, телеметрія власнику `flu-tel`,
  відмова чужому ноутбуку, передача й видалення, вимкнена передача в зібраній програмі;
- правила роутера (Starlink, masquerade, UDP-відео), пошук роутера (MNDP, режим CAP, USB-перехідник),
  пароль, дрейф, скрипти переїзду, розбір параметрів;
- запис камер у налаштування Termite;
- правила арбітра й живий прогін арбітра з фейковим НРК і трьома операторами;
- веб-інтерфейс, обидві мови, запуск команд із зібраної програми.

## Перевірити на залізі

Каркас зібраний і протестований без заліза. Перед бойовим використанням перевірте
на одному НРК і одному сервері:

**MikroTik:**
- [ ] `robot.rsc` застосовується повністю через netinstall `-r -s` і через `reset-configuration run-after-reset`. Якщо якийсь рядок не пройшов, відбиток у `fleet bench mikrotik` не збіжиться; причину дивіться в `/log print`;
- [ ] імена портів (`ether1..5`) і WAN (`ethernet` або `lte`) відповідають вашій моделі (`base/platforms.yaml`);
- [ ] `reset-configuration` по SSH проходить без інтерактивного підтвердження;
- [ ] автовідкат під час переїзду: `:execute` з `:delay` переживає закриття SSH-сесії;
- [ ] RouterOS заново резолвить DNS-ім'я endpoint WireGuard після зміни IP сервера. Якщо ні — потрібен скрипт у планувальнику;
- [ ] пошук і перепрошивка через Starlink: Starlink у режимі роутера (не bypass), ноутбук у його Wi-Fi.

**Пристрої й телеметрія (нова прошивка):**
- [ ] пошук пристроїв у портах 2–4 перед прошивкою знаходить камери й адаптер ФК замовника (`192.168.15.x`);
- [ ] активний опит (`/tool ip-scan address-range=…`) знаходить камеру, яку ніхто не дивиться, і тимчасова адреса
  після нього зникає (`/ip address print`);
- [ ] перепрошивка через тунель: роутер повертається через тунель, камери й телеметрія на місці;
- [ ] приймальний тест: камери й адаптер ФК відповідають роутеру (ping або ARP);
- [ ] після прошивки камери видно через тунель і в Termite, без ручних правил на роутері;
- [ ] телеметрія адаптера ФК у режимі UDP доходить пілоту через сервер (`flu-tel`), а керування й пульт — назад;
- [ ] передача НРК іншому пілоту (версія з репозиторію): новий пілот бачить НРК і отримує телеметрію, попередній — ні.

**Польотний контролер:**
- [ ] мережевий адаптер ФК працює TCP-сервером (наприклад, `192.168.88.2:5760`) або сам шле UDP (див. «Телеметрія, яку адаптер ФК шле сам»). Це налаштовується утилітою чи веб-сторінкою адаптера; інший варіант — `fc.link: ardupilot-net`;
- [ ] MAVLink SYSID у ФК унікальний (= slot НРК), якщо один пілот веде кілька НРК;
- [ ] імена параметрів вашої прошивки: `legacy` (SYSID_*) або `mav` (MAV_*), див. `fc.param_names`;
- [ ] MAVLink по TCP через LTE: затримка команд під час втрат пакетів. Якщо заважає, наступний крок — UDP-транспорт в арбітрі.

**Камери:**
- [ ] виробник, логін, пароль і RTSP-шляхи у `base/platforms.yaml` відповідають вашим камерам (за замовчуванням Dahua);
- [ ] якщо переносите камери `fleet bench cameras`: зміна IP через ISAPI (Hikvision) або CGI (Dahua) на ваших моделях; у Dahua інтерфейс може називатися `eth2`.

**Сервер:**
- [ ] `docker compose up --build` арбітра і MediaMTX `1.21.1` на сервері (managed);
- [ ] WebRTC через тунель (managed).

Не автоматизовано:
- активація камер і зміна їхнього пароля;
- налаштування пульта в Termite і вибір MAVLink-підключення, якщо адаптер ФК — TCP-сервер;
- прошивка самого ArduPilot (`.apj`): робиться uploader.py або Mission Planner;
- калібрування компаса й IMU.
