# FLU fleet — конвеєр прошивки та обслуговування НРК

НРК (наземні роботизовані комплекси), майданчики й оператори описуються в YAML.
Усі конфіги — MikroTik, параметри ArduPilot, сервер WireGuard, MediaMTX, арбітр,
конфіги операторів — збираються з цих описів командою `fleet`. Руками на залізі
нічого не вводиться.

**Покрокова інструкція «чистий ноутбук + порожній сервер → готовий НРК» зі скріншотами:
[docs/flow.md](docs/flow.md).**

## Швидкий старт

На ноутбуці: двічі клацнути **`setup.cmd`**. Установник поставить Python 3.14, WireGuard
і fleet, створить ярлик «FLU fleet» і відкриє майстер першого налаштування:
адреса сервера, ім'я пілота, номер НРК — і одна кнопка «Створити на сервері».

Далі програма запускається ярликом «FLU fleet» або `fleet-ui.cmd` у теці репозиторію. Чорне вікно не
закривайте: поки воно відкрите, працює програма. Повторний запуск не стартує другу копію, а лише відкриває
браузер. Якщо після `git pull` змінився `pyproject.toml`, `fleet-ui.cmd` сам оновить залежності.

Для розробки (тести, скріншоти документації):

```powershell
py -3.14 -m venv .venv
.venv\Scripts\pip install -e .[dev,docs]
.venv\Scripts\pytest
```

Підтримується Python 3.11–3.14. На 3.15 поки немає готових збірок `pymavlink` і `PyYAML`.

Мова: українська за замовчуванням, англійська — `fleet --lang en ...` або `FLEET_LANG=en`.
У веб-інтерфейсі й панелі операторів мова перемикається кнопками UK / EN у шапці.

## Інтерфейс для стенда

`fleet ui` відкриває `http://127.0.0.1:8765`:

- **майданчики:** розгортання сервера, файли підключення для сервера замовника;
- **таблиця НРК:** майданчик, слот, стан MikroTik і результат останнього тесту;
- **покрокова прошивка вибраного НРК:** реєстрація → MikroTik → камери → польотний
  контролер (список COM-портів підставляється сам) → сервер → приймальний тест;
- **переїзд НРК, перегляд зібраних конфігів і консоль** із виводом команд.

Кнопки запускають ті самі команди `fleet`, що й у терміналі, по одній за раз.
Інтерфейс слухає лише 127.0.0.1 і не віддає файли з `secrets/`.
Пароль камер показується за кнопкою: він потрібен для активації.

## Адресний план

Усередині кожного НРК мережа однакова:

| Адреса | Пристрій | Порт MikroTik (flu-v1) |
|---|---|---|
| 192.168.88.1 | MikroTik | — |
| 192.168.88.2 | ФК / мережевий адаптер ФК, MAVLink TCP 5760 | ether2 |
| 192.168.88.11 | камера 1 | ether3 |
| 192.168.88.12 | камера 2 | ether4 |
| 192.168.88.100–199 | DHCP: ноутбук на стенді | ether5 |

Технічне ім'я НРК — `nrk-<id>` (наприклад, `nrk-001`): воно ж ідентифікатор
MikroTik, імена файлів і відеопотоків. Ззовні НРК видно через тунель свого
майданчика; адреси виводяться зі `slot` (номер НРК на майданчику, він же MAVLink SYSID):

- **тунель** — `tunnel + 1 + slot`; сервер майданчика — `.1`;
- **пристрої** — блок `/28` з `robot_lans`: MikroTik робить netmap цього блоку в `192.168.88.0/28`.
  Наприклад, на майданчику з `robot_lans: 10.150.16.0/20` у НРК зі slot 2 камера 2 видна як `10.150.16.28`;
- **оператори** — `operators + id оператора`.

`fleet check` не пропустить перетинів між майданчиками, з `192.168.88.0/24` і з CGNAT `100.64.0.0/10`.

## Три сценарії

| | Сценарій | `kind` | Що робить fleet |
|---|---|---|---|
| 1 | Наш сервер | `managed` | `deploy-server --site` ставить окремий екземпляр стеку під замовника. Кілька екземплярів живуть на одному VPS: кожен на своєму порту WireGuard і своїй адресі в тунелі |
| 2 | Сервер замовника, обслуговуємо ми | `managed` | те саме, лише `host` — VPS замовника (Ubuntu/Debian, 1 vCPU, 1–2 ГБ, публічний IP, SSH-доступ для нас) |
| 3 | Власний сервер замовника | `external` | `fleet kit --site` збирає файли підключення для їхнього адміністратора: піри WireGuard, адреси, окремо паролі камер |

Стек managed-майданчика: WireGuard (`wg-quick`), MediaMTX і арбітр у Docker. Сервер
не пересилає трафік між пірами: оператори працюють лише із сервісами сервера.

`endpoint` майданчика краще задавати DNS-ім'ям. Тоді майданчик можна перенести
на інший сервер (сценарій 1 → 2), не чіпаючи НРК: розгортання на новий host з тими
самими ключами з `secrets/`, потім зміна DNS.

## Новий НРК

Детально, зі скріншотами — у [docs/flow.md](docs/flow.md). Коротко:

1. **Майстер** (`fleet setup --server <IP> --pilot <ім'я> --serial <номер>`): записує сервер,
   пілота й НРК в інвентар, ставить SSH-ключ на сервер, реєструє НРК, розгортає сервер і
   додає тунель пілота у WireGuard. Наступні НРК — той самий майстер з новим номером.
2. Для сервера замовника замість розгортання — `fleet kit --site <майданчик>`.
3. Окремі кроки теж доступні: `fleet provision --id 4`, `fleet deploy-server --site main`, `fleet wg-install --pilot ivan`.
4. **MikroTik**: Netinstall з `robot.rsc` або `fleet bench mikrotik --id 4 --password <з наліпки>`.
5. **Камери**: активуйте паролем з реєстрації, потім `fleet bench cameras --id 4`.
6. **ФК** по USB: `fleet fc --id 4 --connect COM5 --push --reboot`.
7. **Приймальний тест**: `fleet test --id 4`, звіт — у `build/reports/`.

## Переїзд на інший майданчик

```bash
fleet move --id 4 --to customer-vps
```

1. Новий майданчик отримує пір НРК: для managed — автоматичне розгортання, для external — підтвердження, що замовник додав пір.
2. На MikroTik поруч зі старим тунелем піднімається новий, з автовідкатом через 10 хвилин.
3. Є handshake — переїзд підтверджується, старий тунель видаляється. Немає — зміни одразу відкочуються, НРК лишається на місці.

Віддалений доступ до MikroTik іде сервісним тунелем, а без нього — через SSH-сервер managed-майданчика.
`slot` за можливості зберігається, щоб не міняти SYSID у ФК.

## Оператори й передача НРК

Оператор імпортує свій конфіг з `build/sites/<майданчик>/operators/` у WireGuard.
Там само лежить `README.md` з адресами НРК і камер. Далі оператор:

- відкриває панель `http://<сервер майданчика>:8080`: там видно, хто чим володіє, і там же НРК можна взяти, передати, звільнити або зупинити;
- підключає QGroundControl або Mission Planner по TCP до `<сервер>:5760+slot` (GCS sysid лишається 255);
- дивиться відео за `rtsp://<сервер>:8554/<нрк>-cam1` або через WebRTC на порту 8889.

Правила арбітра:
- телеметрія йде всім;
- команди проходять лише від власника;
- не-власник може читати параметри й місію та натиснути «Стоп»;
- heartbeat до НРК проходить лише від власника, тож якщо власник зник, через `FS_GCS_TIMEOUT` секунд НРК стає в Hold;
- під час передачі арбітр сам ставить НРК у Hold. Новий власник приймає НРК, лише коли вже підключений до нього;
- диспетчер може забрати НРК примусово;
- усе пишеться в журнал `state/audit.jsonl` на сервері.

## Секрети

`secrets/` у git не потрапляє. **Без нього майданчики не можна обслуговувати**: ключі
серверів і НРК не відновити. fleet не перестворює втрачений ключ сервера мовчки,
якщо на майданчику вже є НРК (`--new-key` — лише свідомо). Для командної роботи
зашифруйте теку через sops + age і зберігайте в git або тримайте резервну копію.

## Тести

```bash
.venv\Scripts\pytest
```

Тести працюють на власному інвентарі з `tests/fixtures/` (по майданчику на кожен
сценарій) і не чіпають справжній. Покрито:
- перевірка інвентарю й адресний план;
- збирання всіх конфігів і узгодженість ключів між НРК і сервером;
- скрипти переїзду, розбір параметрів;
- правила арбітра й живий прогін арбітра з фейковим НРК і трьома операторами;
- веб-інтерфейс і обидві мови.

## Перевірити на залізі

Каркас зібраний і протестований без заліза. Перед бойовим використанням перевірте
на одному НРК і одному сервері:

**MikroTik:**
- [ ] `robot.rsc` застосовується повністю через netinstall `-r -s` і через `reset-configuration run-after-reset`. Якщо якийсь рядок не пройшов, відбиток у `fleet bench mikrotik` не збіжиться; причину дивіться в `/log print`;
- [ ] імена портів (`ether1..5`) і WAN (`ethernet` або `lte`) відповідають вашій моделі (`base/platforms.yaml`);
- [ ] `reset-configuration` по SSH проходить без інтерактивного підтвердження;
- [ ] автовідкат під час переїзду: `:execute` з `:delay` переживає закриття SSH-сесії;
- [ ] RouterOS заново резолвить DNS-ім'я endpoint WireGuard після зміни IP сервера. Якщо ні — потрібен скрипт у планувальнику.

**Польотний контролер:**
- [ ] мережевий адаптер ФК працює TCP-сервером на `192.168.88.2:5760`. Це налаштовується утилітою виробника адаптера; інший варіант — `fc.link: ardupilot-net`;
- [ ] імена параметрів вашої прошивки: `legacy` (SYSID_*) або `mav` (MAV_*), див. `fc.param_names`;
- [ ] MAVLink по TCP через LTE: затримка команд під час втрат пакетів. Якщо заважає, наступний крок — UDP-транспорт в арбітрі.

**Камери:**
- [ ] зміна IP через ISAPI (Hikvision) або CGI (Dahua) на ваших моделях; у Dahua інтерфейс може називатися `eth2`.

**Сервер:**
- [ ] `docker compose up --build` арбітра і MediaMTX `1.21.1` на сервері;
- [ ] WebRTC через тунель.

Не автоматизовано:
- активація камер і зміна їхнього пароля;
- прошивка самого ArduPilot (`.apj`): робиться uploader.py або Mission Planner;
- калібрування компаса й IMU.
